# Диагностика по стадиям

[Документация](index.md) · [English](../en/troubleshooting.md)

Сначала найдите первую содержательную ошибку и команду, затем определите стадию.
Предупреждение и ненулевой exit code — разные наблюдения. Сохраните версии,
backend, профиль, source/build paths и overrides. Не меняйте toolchain при
воспроизведении ошибки без причины.

| Стадия | Что исследовать | Что успех не доказывает |
| --- | --- | --- |
| Configure | YAML/IOC, пути, компоненты, кэш, сообщения CMake | Создание корректного Ninja-графа |
| Generate | Имена целей, generator expressions, свойства и граф | Компилируемость исходников |
| Compile | Команду конкретного C/C++/ASM-файла, include, defines, CPU/ABI | Разрешение символов при линковке |
| Link | Startup/ENTRY, символы, архивы, linker script и MEMORY | Корректный запуск MCU |
| Post-build | objcopy, CRC-команду, входные и выходные файлы | Совпадение CRC с проверкой загрузчика |
| Run | SP/PC, векторы, карту памяти, fault-регистры доступного ядра | Причину сбоя без наблюдений |

## Кэш и воспроизведение

Автор обычно выполняет в VS Code удаление кэша и перенастройку после правки YAML.
Это допустимый workflow. Если исследуется stale cache, сначала сохраните исходный
лог/команду, затем сравните со свежей build-папкой. Пропуск -D не удаляет значение.
Настройки IDE/file watchers не предполагаются автоматически; Configure можно
запустить явно. См. [режимы разработки](development.md) и [семантику](reference/0.9.2/semantics.md).

**Версия 0.9.2** (ТЗ 3.6.6): Configure не зависит от `stm32_config.yml`, IOC и
файла профилей, а производные значения могут остаться в кэше (E001). После
изменения этих файлов удалите `CMakeCache.txt` (или всю build-папку) и повторите
Configure. В 0.9.3 эти файлы — зависимости Configure: сборка перезапускает его
сама, а производные значения обновляются при каждом Configure.

## RAM и диагностические флаги

`validate_linker_script` суммирует распознанные RAM-секции .ld и сравнивает их
с базой MCU. В 0.9.2 несовпадение не останавливает Configure; оно не означает,
что причиной стал heap+stack. Проверка не валидирует адресные пересечения или SP.
Если секции не распознаны, выдаётся предупреждение и проверка пропускается;
последующее равенство в логе не является доказательством корректности скрипта.
Arduino пропускает этот механизм.

`log_target_properties` выводит свойства цели, а не все разрешённые команды
компилятора. `verbose_build` не запускает сборку. Сверяйте compile_commands.json
для нужного файла, языка и цели. [Reference](reference/0.9.2/diagnostics.md).

## Конкретные сообщения

- `hal_conf.h` отсутствует при Configure: проверьте use_hal/backend, имя семейства
  и include-пути цели. Ошибка компилятора о том же файле относится к Compile —
  смотрите реальную команду, в том числе отдельную библиотеку.
- `Reset_Handler` не разрешён при Link: проверьте startup, ENTRY, имена символов
  и состав линковки. Не включайте CMSIS вслепую и не добавляйте второй startup;
  bare metal может иметь собственный reset/vector code.
- Ошибка FindFreeRTOS: исследуйте конкретную строку, аргументы и версии. Обратные
  слэши Windows — возможная гипотеза, а не универсальный диагноз.
- HardFault требует данных исполнения; сравнение RAM при Configure не определяет
  его причину. Не меняйте heap/stack или MEMORY без подтверждения.
- CRC: используйте [E004](errata/E004.md) и [E006](errata/E006.md).
  Сгенерированная команда не доказывает её успешное выполнение; нулевое значение
  само по себе не является ошибкой.

## Автоматическое покрытие

| CTest (префикс configure.) | Ожидание |
| --- | --- |
| diagnostics-toggle | Вывод свойств и сравнения 128K > 20K включается, выключается и снова включается при повторном Configure; все три шага успешны. |
| diagnostics-unrecognized-ram | Нет распознанных RAM-секций: предупреждение и успешный Configure. |
| diagnostics-missing-hal-conf | HAL включён, конфигурационного заголовка нет в include-пути: Configure завершается ошибкой с нужной причиной. |
