# JSON Schema конфигурации

[Документация](index.md) · [English](../en/schema.md)

С 0.10.0 репозиторий содержит [схему](../../schema/stm32-config.schema.json)
для проверки структуры конфигурации. Это JSON Schema
[Draft 2020-12](https://json-schema.org/draft/2020-12/json-schema-validation).
Фреймворк не запускает её при Configure и не требует Python-пакетов схемы от
проектов пользователей. Подключение к редактору остаётся на усмотрение разработчика.

Схема проверяет известные типы и перечисления, целые размеры памяти, секции
`arduino`, `stm32_cmake_yml`, `crc`, `cppcheck`, профили без `_`, `include` и
значения `_append`. Вложенные и плоские формы известных ключей описаны явно.
Неизвестные ключи разрешены: проект может использовать собственные настройки.
Поэтому успешная проверка не гарантирует отсутствия опечаток в именах ключей.

Отсутствующие ключи, `null`, пустая строка и пустой массив разрешены; схема не
вставляет defaults. Файл подключения может содержать только часть конфигурации.
Проверка файла не выполняет слияние `include`, выбор профиля, overrides или чтение
IOC. Она не проверяет наличие файлов, доступность MCU/библиотек, конфликты
уплощённых имён, linker script, компилятор или успешность сборки. Для этого
остаются Configure/Generate и проверки прошивок.

Схема описывает поддерживаемые значения: например, неизвестный backend не пройдёт
L1, хотя Configure может предупредить и выбрать значение по умолчанию. Это разные
проверки. Для регрессий такого поведения исключение фиксируется по конкретному
ключу, а не отключает проверку всего файла.

## Источник и генерация

Источник — [индекс справочника](../reference-index.json). Поля `yaml_paths` задают
пути ключа в дереве YAML, `schema` — его тип и ограничения. Описания `type` остаются
текстом для человека: генератор не извлекает перечисления из этих строк.
Генерируемый файл не редактируют вручную.

```sh
python ci/config_schema.py
python ci/config_schema.py --check
```

Генерация работает на стандартной библиотеке Python. Проверка L1 требует Python
3.11+ и пакеты из [schema-requirements.txt](../../ci/schema-requirements.txt):

```sh
python -m venv build/schema-venv
# Windows:
build/schema-venv/Scripts/python.exe -m pip install -r ci/schema-requirements.txt
build/schema-venv/Scripts/python.exe ci/check_schema.py
build/schema-venv/Scripts/python.exe -m unittest discover -s tests -p test_config_schema.py
# Linux: замените build/schema-venv/Scripts/python.exe на build/schema-venv/bin/python
```

Проверка читает YAML 1.2 через ruamel.yaml и TOML через `tomllib`; Configure
по-прежнему использует закреплённый yq. L1 не заменяет проверку парсера фреймворка.
Для проверки пресетов также нужны CMake ≥ 3.21 и Ninja.

## Что проверяет CI

Workflow Docs сверяет схему с индексом, проверяет её по метасхеме и валидирует:

- YAML/TOML в `tests/fixtures` и `tests/firmware`;
- содержимое YAML/TOML, записываемое через `write_files` в сценариях повторного Configure;
- YAML [примера с пресетами](presets.md).

[schema-exceptions.json](../../tests/schema-exceptions.json) перечисляет намеренно
ошибочные значения по файлу и JSON Pointer с причиной. Исключение для ошибки
синтаксиса обозначено `<parse>`. Неожиданная ошибка, исчезнувшая ожидаемая ошибка
или исключение для удалённого файла проваливают L1. Остальные значения того же
файла продолжают проверяться. Cache overrides из командной строки и конфигурации,
создаваемые программно прошивочным runner, этим обходом файлов не охватываются.

Пример пресетов дополнительно проверяется CMake на небольшом проекте без языков:
четыре варианта выбирают ожидаемые YAML-профиль, тип и каталог сборки. Эта проверка
подтверждает связи пресетов; сборкой Arduino-прошивки она не является.
