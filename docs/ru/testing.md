# Окружение тестирования

[English](../en/testing.md)

Тестирование использует изолированное Linux-окружение и тестовые проекты CTest.
Существующие проекты с `include(stm32_yml)` не требуют изменений. Тесты вызывают
фреймворк из текущего checkout и проверяют результат Configure/Generate;
компиляция прошивок не выполняется.

## Состав

| Компонент | Закреплённые версии |
| --- | --- |
| Платформа | Linux amd64, Ubuntu 24.04 с фиксированным digest образа |
| Пакеты Ubuntu | Репозитории Ubuntu; установленные версии записываются в образ |
| xPack Arm GCC | 13.3.1-1.1, 14.2.1-1.1, 15.2.1-1.1 |
| CMake | 3.19.8 (минимальная совместимость), 3.28.3 (опорное окружение) |
| Ninja / Mike Farah yq | 1.12.1 / 4.44.3 |
| stm32-cmake | Коммит указан в lock-файле |
| STM32Cube | F0 1.11.6, F1 1.8.7, F3 1.11.5, F4 1.28.3, F7 1.17.3, G4 1.6.3, H5 1.7.0, H7 1.13.0 |
| FreeRTOS-Kernel | 11.3.1 (`/opt/FreeRTOS-Kernel/11.3.1`, для `freertos_version: external`) |
| Arduino Core STM32 / ETL | 2.12.0 / 20.47.1 |

[dependencies.lock.json](../../ci/dependencies.lock.json) содержит SHA-256 архивов
и коммиты исходников. Выбранные подмодули Cube (CMSIS device, HAL и FreeRTOS там,
где это подмодуль) используют gitlinks закреплённых коммитов, а не вершины веток.
Подмодули BSP и прочих middleware не инициализируются. Каталоги примеров
`Projects` и `Utilities` репозиториев Cube не загружаются: частичный клон
(`--filter=blob:none`) и sparse-checkout по полю `sparse_exclude` lock-файла
сокращают Cube с 3,9 до 1,3 ГБ. Архивы и исходники устанавливаются параллельно
в 4 потока, лог каждого элемента печатается целиком. Git-метаданные и лицензии
сохраняются для проверки. Версии пакетов Ubuntu записываются в образе в
`/opt/stm32-yml-ci/packages.txt`.

QEMU **11.0.0** (заранее собранный из исходников, [tools/qemu](../../tools/qemu/README.md)) и Renode
входят в отдельный образ эмуляции ([ci/emulation](../../ci/emulation/Dockerfile)); в этот образ они не включены. Arduino-проектам по-прежнему нужны
свои CMake-обёртки ядра и библиотек. Образ не содержит копию stm32-cmake-yml.

## Сборка и проверка

Нужен Docker с Linux-контейнерами. Запуск из корня репозитория, одинаково в
PowerShell и Linux shell:

```sh
docker build --platform linux/amd64 -f ci/docker/Dockerfile -t stm32-yml-ci:local .
docker run --rm --network none stm32-yml-ci:local
```

Первая сборка скачивает три toolchain и исходники Cube: потребуется несколько ГБ
диска и время на загрузку. Последующие сборки используют кэш слоёв Docker.
Отдельный ignore-файл Dockerfile передаёт только файлы окружения.
Контрольные суммы проверяются до распаковки. Ошибка установки останавливает сборку.

Команда по умолчанию проверяет версии инструментов, преобразование YAML,
коммиты исходников и наличие необходимых файлов зависимостей. Затем выполняет
конфигурацию маленького C/C++/ASM-проекта для всех шести сочетаний GCC/CMake и
проверяет генерацию файлов Ninja. CMake выполняет собственные проверки
компилятора, но `cmake --build` не вызывается. Это проверка готовности окружения,
**не** поведения фреймворка, линковки прошивки, корректности CRC или симуляции
периферии MCU. Проверка работает без сети.

## Выбор инструментов и подключение рабочей копии

По умолчанию: GCC `14.2.1-1.1`, CMake `3.28.3`. Переменные `GCC_VERSION` и
`CMAKE_VERSION` выбирают установленную версию. Неизвестные и пустые значения
немедленно приводят к ошибке.

```sh
docker run --rm --network none -e GCC_VERSION=13.3.1-1.1 -e CMAKE_VERSION=3.19.8 stm32-yml-ci:local cmake --version
docker run --rm --network none -e GCC_VERSION=15.2.1-1.1 stm32-yml-ci:local arm-none-eabi-gcc --version
```

Открыть shell с текущей рабочей копией, подключённой только для чтения.
Результаты размещайте в `/tmp/build/...` или отдельном writable mount. Linux:

```sh
docker run --rm -it --network none --mount "type=bind,source=$(pwd),target=/workspace,readonly" stm32-yml-ci:local bash
```

PowerShell:

```powershell
docker run --rm -it --network none --mount "type=bind,source=$($PWD.Path),target=/workspace,readonly" stm32-yml-ci:local bash
```

Внутри контейнера:

- Toolchain: `$STM32_TOOLCHAIN_PATH`, выбранные исполняемые файлы также в `PATH`.
- stm32-cmake: `/opt/modules/stm32-cmake`.
- Cube: `/opt/STM32Cube/Repository/STM32Cube_FW_<family>_V<version>`;
  `CMAKE_USER_HOME=/opt` включает существующий механизм поиска фреймворка.
- Arduino Core: `/opt/Arduino_Core_STM32/2.12.0`.
- ETL: `/opt/etl/20.47.1`.
- Проверяемый фреймворк: `/workspace`, подключается вызывающей стороной.

Используйте отдельные build-папки для проекта/профиля/GCC/CMake/типа сборки.
Сохраняйте выбранное окружение при запуске команд: используйте `bash`, а не
login shell, который может сбросить `PATH`. Эти же Docker-команды доступны в
терминале VS Code. Интерактивная отладка и launch-конфигурации добавятся позднее.

## Обновление и CI

Workflow окружения собирает образ и проверяет его без сетевого доступа.
Отдельный workflow `Configure tests` запускается при push в `main`, `codex/**` и `claude/**`, а также вручную. Он собирает образ один раз и проверяет шесть пар инструментов
в одном задании, продолжая работу после неудачной пары. Оба workflow не публикуют
образы и не собирают прошивки. Отсутствие фильтра по путям позволяет
проверять каждый push ветки независимо от того, какие файлы изменены.

Обновляйте версии и хэши вместе в lock-файле, проверяйте источники upstream,
затем пересобирайте и проверяйте образ. При изменении Ubuntu также обновляйте
digest в Dockerfile, чтобы он совпадал с lock-файлом.
CMake 3.28.3 — фиксированная опорная версия, а не последняя доступная.
Системные библиотеки и Python получают обновления Ubuntu: закреплены инструменты
тестирования и исходники зависимостей, но не каждый пакет ОС и не байты итогового
образа. Доступность сервиса снимков Ubuntu не требуется.

## Проверки конфигурации фреймворка

[tests/cases.json](../../tests/cases.json) описывает 139 сценариев, каждый из
которых запускается на трёх версиях GCC и двух версиях CMake из lock-файла:
**834 выполнения тестов**. Двадцать шесть сценариев выполняют от двух до тринадцати
последовательных конфигураций в одной build-папке.

| Область | Проверки |
| --- | --- |
| Значения по умолчанию и зависимости | F411 (BlackPill) и F103 (BluePill), реальные цели CMSIS/HAL, heap/stack по умолчанию, стандарты C/C++ |
| Профили одного MCU | Замена списков, дополнение, замена с последующим дополнением, исходники, внешние профили (только секция `profiles:`), ключи только из профиля и override без объявления в корне, приоритет скалярных overrides |
| IOC и приоритеты YAML | STM32F103C8T6, параметры из IOC, приоритет YAML/профиля/override, значения ручного режима для неполного IOC, отсутствие IOC |
| Bare metal | Без CMSIS/HAL/FreeRTOS и доступного Cube-репозитория, явные флаги CPU и локальный linker template |
| Значения YAML | Скаляры без кавычек, `false`, нулевой heap, null/пустые значения, замена и дополнение пустых списков |
| Повторная настройка | Замена и сброс исходников/defines профиля, сохранение overrides и явное удаление из кэша через `-U`, перезапуск Configure при изменении YAML, IOC и файла профилей |
| Регрессии профилей | Список внешних профилей, обновление heap/stack в шаблоне, MCU и defines после переключения профиля |
| Флаги языков | Нормализация и раздельное применение флагов/определений C и C++ в `compile_commands.json` |
| Linker | Явный `.ld`, поиск шаблона в `linker_script_dir`, подстановка heap/stack, формат размеров во всех режимах, предупреждение о неприменённых heap/stack, сохранение READONLY и секции checksum |
| CRC | Наличие/отсутствие сгенерированной post-build команды, аргументы секции и размера Flash |
| Arduino | Пользовательские обёртки ядра и библиотеки, параметры профиля, общие compile definitions, `use_core_main: false` |
| Диагностика | Отсутствующий/некорректный YAML, отсутствие linker/core, неверный размер памяти, HAL без CMSIS, список профилей и предупреждение о неизвестном профиле, предупреждения о неизвестных значениях перечислимых ключей и их отсутствие для пустых значений |

Это небольшие примеры **только для Configure/Generate**, а не готовые прошивки
для плат. Обёртка Arduino использует настоящий исходник закреплённого ядра, но
не описывает полную конфигурацию платы/variant. Её toolchain предоставляет
функцию вывода размера, которую ожидает текущий фреймворк, по аналогии с
toolchain проекта-потребителя. Синтетический linker template проверяет
подстановки и сохранение секций, а не правильность размещения в памяти.
Исполнение CRC, линковка прошивок, периферия, QEMU и Renode остаются за рамками
этапа. При определении компилятора CMake может компилировать собственные пробы.

Положительный сценарий требует успешного завершения CMake, создания Ninja-файла,
кэша и базы команд компиляции, а также совпадения параметров или свойств целей.
Отрицательный сценарий требует и ошибки, и конкретной диагностики: случайная
проблема с компилятором не засчитается как успех. Сохраняется текущее поведение:
неизвестный профиль вызывает предупреждение и продолжение настройки;
`STM32_YML_PROFILE=list` выводит имена и завершается ошибкой. Каждый сценарий
начинается со свежего кэша; многошаговые сценарии намеренно используют его повторно
и проверяют каждый шаг. Отсутствие аргумента `-D` не удаляет его из CMakeCache:
для удаления override нужен `-USTM32_YML_OVERRIDE_stack_size`, для возврата
к базовому конфигу — `-DSTM32_YML_PROFILE=`.

Регрессионные сценарии также проверяют список внешних профилей и смену размеров
памяти или MCU в одной build-папке. `MCU`, `HEAP_SIZE` и `STACK_SIZE` — производные
записи кэша; теперь они следуют вычисленной конфигурации при каждом Configure
(`HEAP_SIZE`/`STACK_SIZE` — при генерации локального шаблона). Для переопределения
используйте входные параметры `-DSTM32_YML_OVERRIDE_mcu=...`,
`-DSTM32_YML_OVERRIDE_heap_size=...`, `-DSTM32_YML_OVERRIDE_stack_size=...`.
Прямые `-DMCU`, `-DHEAP_SIZE` и `-DSTACK_SIZE` больше не имеют приоритета над
вычисленной YAML-конфигурацией. Для смены компилятора/toolchain по-прежнему
нужна отдельная build-папка.

### Происхождение F1-примера и будущая симуляция

Сокращённый [bluepill-hsi.ioc](../../tests/fixtures/project/bluepill-hsi.ioc)
использует ключи ProjectManager из авторского
[примера 03-blink](https://github.com/ViacheslavMezentsev/demo-stm32-cmake/blob/0eaf00af7378ba93d74205d60fc98493b6632f2a/stm32f1xx/03-blink/03-blink.ioc).
Там указан `STM32F103C8Tx` (парсер убирает завершающий `x`); тестовый YAML также
проверяет полное имя `STM32F103C8T6`. Исходный пример использует HSE/PLL, 72 МГц.
В сокращённом примере заданы HSI, 8 МГц, без выбора PLL и версия Cube F1 1.8.7
из lock-файла окружения. Это не полный проект CubeMX; регенерация в CubeMX не
проверялась. Проверяется разбор конфигурации, а не тактирование: фреймворк не
генерирует и не исполняет `SystemClock_Config`. В будущих прошивках нужно явно
реализовать HSI с выключенным PLL и проверить работу в симуляторе.

В авторском `stm32f1xx/02-semihosting/.vscode/tasks.json` QEMU запускается с
`-semihosting`; этот параметр следует сохранить в будущих semihosting-тестах.
Примеры служат справочным материалом и не скачиваются при запуске набора.
Скаляры YAML — имена MCU, пути, `1K` — оставлены без кавычек. Кавычки нужны,
когда этого требует синтаксис YAML или сохранение строкового типа.

Полная матрица запускается из корня репозитория после сборки образа, описанной
выше. PowerShell, в том числе терминал VS Code:

```powershell
New-Item -ItemType Directory -Force build/configure-tests | Out-Null
docker run --rm --network none --mount "type=bind,source=$($PWD.Path),target=/workspace,readonly" --mount "type=bind,source=$($PWD.Path)/build/configure-tests,target=/results" stm32-yml-ci:local python3 /workspace/ci/run_configure_tests.py --output /results
```

Linux:

```sh
mkdir -p build/configure-tests
docker run --rm --network none --user "$(id -u):$(id -g)" --mount "type=bind,source=$PWD,target=/workspace,readonly" --mount "type=bind,source=$PWD/build/configure-tests,target=/results" stm32-yml-ci:local python3 /workspace/ci/run_configure_tests.py --output /results
```

Для одной пары инструментов откройте shell контейнера с этими двумя mount и
при необходимости `-e GCC_VERSION=... -e CMAKE_VERSION=...`, затем выполните:

```sh
cmake -S /workspace/tests -B /results/single -G Ninja
cd /results/single
ctest --output-on-failure -j 4
ctest --output-on-failure -R '^configure.profile-'
```

Используйте отдельный каталог `single` для каждой пары. Вариант с `cd` совместим
с CMake 3.19. Корневой `CMakeLists.txt` и presets для проектов-потребителей не
добавляются; точка входа тестов находится в `tests/`.

В выходной папке сохраняются `summary.json`, логи CTest, копии исходников и
сгенерированные файлы. Для каждого шага сценария сохраняются `step-N/configure.log`
и снимки кэша, Ninja-файла, базы команд компиляции, linker scripts и свойств.
Повторные запуски сохраняют отдельные папки сценариев для диагностики и занимают
место до удаления сгенерированных результатов. GitHub сохраняет выбранные файлы
в артефакте `configure-diagnostics` на 14 дней, в том числе при падении тестов.
Симлинки на ядро и исходники зависимостей в артефакт не включаются.

Для нового сценария дополните `tests/cases.json` и при необходимости тестовые
файлы. Проверяйте наблюдаемый результат, не копируйте логику фреймворка в тесты.
Перед изменением поведения в следующем изменении добавляйте регрессионный сценарий.
Имена тестов должны оставаться уникальными.

### Границы профилей и пустые overrides

Три дополнительных многошаговых сценария проверяют изоляцию допустимых имён
`Rev`/`RevB` по исходникам, определениям и размерам linker template; возврат от
непустого override к значению профиля при `-DSTM32_YML_OVERRIDE_stack_size=`;
сброс и повторное применение внешнего профиля без оставшихся определений.
Пустой override игнорируется и не означает нулевой размер. `_` в именах профилей
остаётся вне контракта. Код фреймворка для этих проверок не менялся.

Рабочий процесс VS Code с удалением кэша и ответственность за startup в bare metal
описаны в [режимах разработки](development.md).

### Подключение исходников

Три новых сценария проверяют каталог с CMakeLists, общую цель для вложенных C/C++
и корневого C, пути include и разделение языковых флагов в compile_commands.json.
Отсутствующий файл предупреждает; каталог без CMakeLists завершает Configure
ошибкой. [Руководство и границы покрытия](simple-sources.md).

С 2026-09-24 проверки запускаются без PR по push рабочих веток `codex/**`, `claude/**`
и main. [Порядок слияния](maintenance.md).

### Библиотечные модули

Три сценария проверяют явную связь с STATIC-библиотекой, отсутствие автоматической
связи по одному sources и ошибку неизвестного ALIAS. Проверяются команды C/C++,
PUBLIC/PRIVATE compile-свойства и INTERFACE-настройки; линковка не выполняется.
[Руководство](modules.md).

### Диагностика

Три сценария проверяют переключение log_target_properties/validate_linker_script
в одном кэше, нефатальное несовпадение RAM, предупреждение о пропуске проверки
нераспознанной RAM и ошибку отсутствующего hal_conf. [Пределы диагностики](troubleshooting.md).

### Диагностика версии YAML

Восемь сценариев `version-*` проверяют совпадение, отсутствие, пустую, более старую и более новую версию, отключение сравнения в корне YAML и выполнение сравнения до профиля/override. Все сценарии должны завершить Configure/Generate успешно; предупреждение не является отказом. Это проверка диагностики 0.9.2, а не гарантия совместимости конфигураций будущих версий. Прошивки не собираются.

### FreeRTOS из STM32Cube

Девять сценариев `freertos-*` используют реальные закреплённые пакеты CubeF4 и stm32-cmake из контейнера. Минимальный YAML проверяет порт ARM_CM4F, Heap::4/Heap::2, Timers, EventGroups, StreamBuffer и отсутствие обёртки / CMSIS-RTOS v1 / v2 по свойству LINK_LIBRARIES и успешной генерации Ninja. Профиль `gcs` отражает набор параметров предоставленного автором `mcu_gcs_web_board`; профиль `demo` — `demo-stm32-cmake/stm32f4xx/ethernet-rndis-nicokorn`. Исходные проекты изучены только для чтения; их сетевые исходники не копируются и не собираются.

Отдельно проверяются отсутствие порта, два порта и неизвестный компонент. Отключённый FreeRTOS не должен обрабатывать даже некорректный список компонентов. `freertos-required-package` запрещает find_package через `CMAKE_DISABLE_FIND_PACKAGE_FreeRTOS=TRUE` и ожидает отказ обязательной зависимости; это управляемая имитация недоступного пакета, не проверка физически повреждённого Cube.

Значение `freertos_version` без IOC по умолчанию проверяется через выбранное пространство целей Cube; обёртка при отсутствующем `cmsis_rtos_api` не подключается. External FreeRTOS и автоматический выбор из IOC этим набором не покрыты. Fixture намеренно не содержит FreeRTOSConfig.h: Configure/Generate не проверяет его содержимое и не доказывает корректность планировщика, обработчиков прерываний, кучи или прошивки. Перед сборкой потребуются настройки приложения и согласованный сценарий.

### FreeRTOS из IOC

Семь сценариев `freertos-ioc-*` дополняют ручную конфигурацию выше. Сокращённые IOC-файлы включают маркер FREERTOS и выбор CMSIS-RTOS; проверяются автоматические ARM_CM3/Heap::4/v1 для F1 и ARM_CM4F/Heap::4/v2 для F4. F4-маркеры основаны на предоставленном автором примере `mcu_gcs_web_board`; F1 — синтетический вариант с тем же форматом полей. Это входные данные парсера, не полные проекты CubeMX и не реализация настройки HSI.

YAML и профиль могут заменить компоненты на Heap::2 и API на none. Пустые use_freertos, freertos_version, cmsis_rtos_api и список компонентов получают значения из IOC/автоматического выбора. Override false подавляет включение из IOC. `freertos-ioc-reconfigure` проверяет включено → выключено профилем → включено при повторном Configure с общим кэшем; это дополнение к обычной перенастройке с удалением кэша.

Проверяются экспортированные значения, прямые зависимости цели и успешный Generate. Другие семейства и внешняя поставка FreeRTOS проверяются сценариями ниже; совместимость порта с ядром, выполнение задач и настройка часов здесь не проверяются. Прошивки не собираются.

### External FreeRTOS

Режим `freertos_version: external` ([E007](errata/E007.md) исправлена в ветке 0.9.3) проверяется на двух раскладках. `freertos-external-cmake` и `freertos-external-env` берут дерево FreeRTOS пакета CubeF4 через `-DFREERTOS_PATH` и через окружение; `freertos-external-kernel` — FreeRTOS-Kernel 11.3.1 с `cmsis_rtos_api: none` и `v2`. Ожидаются цели `FreeRTOS::<порт>` и `FreeRTOS::<компонент>` без пространства `FreeRTOS::STM32::F4`. Отрицательные сценарии: нет `FREERTOS_PATH`, порт `ARM_CM7_MPU`, которого нет в FreeRTOS-Kernel, и неизвестный компонент. Обёртка CMSIS-RTOS v2 с FreeRTOS-Kernel 11.3.1 и CubeF1 дополнительно собрана вручную (прошивка `freertosQueue` с настройками FreeRTOSConfig.h, которых требует обёртка); запуск такой прошивки не проверялся.

### Ядро MCU, H7 и H5

`h7-single-core-default` проверяет, что одноядерный STM32H743ZI получает ядро M7 и цели `CMSIS::STM32::H743ZI::M7`, `HAL::STM32::H7::M7::*`. `h7-dual-core` проверяет STM32H745ZI: без ядра — ошибка со списком ядер; с M7 и M4 — цели выбранного ядра, а для M4 сумма RAM и предел Flash для CRC берутся по ядру (288K, 1024K). `mcu-core-invalid` проверяет ядро вне списка и ядро для F4. `h7-freertos-cube` проверяет FreeRTOS из CubeH7 с обёрткой v2 в пространстве ядра M7. `h5-cmsis-hal-freertos-external` проверяет H5: CMSIS/HAL, FreeRTOS-Kernel с портом `ARM_CM33_NTZ`, отказ обёртки v2 (в CubeH5 нет FreeRTOS) и CRC с шаблоном. `hal-missing-component` ожидает ошибку Configure до стадии Generate.

### Порт FreeRTOS по IOC

`freertos-ioc-port-table` за тринадцать шагов проверяет таблицу портов для F1, F4, G0, C0, U0, H5, L5, U5, WL (M4, M0PLUS), WB и H7 (M7, M4): MCU подменяется override, FreeRTOS-Kernel подключается как external, поэтому пакеты Cube этих семейств не нужны. `freertos-ioc-port-unknown-family` проверяет предупреждение и `ARM_CM4F` для семейства вне таблицы.

### Дополнительные семейства F0, F3, F7 и G4

| Семейство | MCU | FreeRTOS из IOC | Проверки |
| --- | --- | --- | --- |
| F0 | STM32F030R8 | ARM_CM0, Heap::4, v1 | CMSIS/HAL, профиль LL, bare metal, IOC RTOS |
| F3 | STM32F303VC | ARM_CM4F, Heap::4, v1 | CMSIS/HAL, IOC RTOS |
| F7 | STM32F746NG | ARM_CM7, Heap::4, v1 | CMSIS/HAL, IOC RTOS |
| G4 | STM32G431CB | ARM_CM4F, Heap::4, v1 | CMSIS/HAL, IOC RTOS |

Десять сценариев проверяют реальные импортированные цели и флаги cortex-m0/m4/m7 в compile_commands.json. F0 bare metal задаёт флаги явно и проверяет отсутствие зависимостей CMSIS/HAL/FreeRTOS. Это Configure/Generate, не компиляция и не доказательство работоспособности RTOS на выбранной памяти.

MCU F0, F7 и G4 выбраны по локальным демо `stm32f0xx/03-blink`, `stm32f7xx/03-blink` и `stm32g4xx/03-blink`; F3 — синтетический F303VC. IOC-fixtures сокращены и дополнены маркерами FreeRTOS/v1. Полные IOC из демо не копируются; поле HSI не генерирует реализацию тактирования. Заголовки HAL минимальны и предназначены только для настройки.

CubeF0/F3/F7 добавлены в lockfile по точным коммитам, CubeG4 уже был закреплён. Загружаются только нужные подмодули CMSIS device/HAL, а для F0 ещё FreeRTOS. В выбранных F3/F7 FreeRTOS входит в родительский репозиторий. BSP и прочие подмодули не инициализируются. Корневой репозиторий загружается частичным клоном со sparse-checkout без `Projects` и `Utilities`.

### Системные библиотеки и параметры линковки

Пять сценариев `system-*` проверяют NoSys + Nano, Semihosting + Nano, отключение обеих настроек, пользовательские link_options/linker_directives и повторную смену профиля NoSys → Semihosting → без системной библиотеки. Проверяются прямые зависимости цели, транзитивные specs в сгенерированных LINK_FLAGS Ninja и отсутствие устаревших flags после повторного Configure.

`link_options: [nostartfiles, "-Wl,--cref"]` превращается в опции драйвера `-nostartfiles` и `-Wl,--cref`; `linker_directives: [--print-memory-usage]` передаётся через LINKER и генерирует `-Wl,--print-memory-usage`. В compile_commands.json эти три опции отсутствуют. Тестовый проект содержит одну исполняемую цель, поэтому проверка требует ровно одну строку LINK_FLAGS. Это проверка текущего генератора Ninja, не универсальный разбор всех генераторов CMake.

Пример основан на bare metal без CMSIS/HAL. Файлы specs предоставляются закреплённым xPack/upstream; проверка не вызывает линковщик и не подтверждает набор системных вызовов, работу printf/float или выполнение semihosting. Подготовка реальной тестовой прошивки остаётся отдельным согласуемым этапом.

### Настройка Cppcheck

Пять сценариев `cppcheck-*` проверяют значения C_CPPCHECK/CXX_CPPCHECK и наличие правила `--cppcheck=` в Ninja: defaults, пользовательские аргументы и исключения, возврат к defaults при пустых списках, отсутствие утилиты и включено → выключено → включено с другими параметрами при общем кэше.

Для положительных сценариев CPPCHECK_EXECUTABLE задан явно как `/usr/bin/false` — это тестовый путь к команде, **не анализатор**. Configure/Generate её не запускает. Такие сценарии проверяют формирование интеграции, но не поиск реального Cppcheck в PATH, его запуск, совместимость версий, разбор suppressions самим анализатором или результаты анализа. Сценарий отсутствия использует штатный find_program в закреплённом образе без Cppcheck и требует предупреждения при успешном Generate.

Непустые cppcheck_args заменяют стандартные аргументы. Непустые cppcheck_ignores заменяют стандартные исключения; фрагмент `Vendor SDK` с пробелом сохраняется одним аргументом свойства CMake. Пустые списки восстанавливают defaults, а не удаляют все аргументы/исключения. Точные значения проверяются для обоих языков. Тесты не компилируют прошивку и не выполняют статический анализ.

CMake 3.19 записывает команду в `CMakeFiles/rules.ninja`, а 3.28 — в `build.ninja`; проверка учитывает оба файла.

### Выбор артефактов после сборки

Шесть сценариев `artifacts-*` проверяют команды, объявленные при Configure/Generate: отсутствие параметра, `[bin, hex, map, lss]`, только map, пустой список, неизвестный элемент рядом с bin и смену профилей все форматы → bin → пустой список с общим кэшем. CRC отключён, чтобы его промежуточные BIN-команды не смешивались с проверяемым выбором артефактов.

Проверяются objcopy binary/ihex, objdump -h -S и имена выходных файлов в POST_BUILD Ninja, а для map — свойство LINK_OPTIONS и итоговый флаг линкера. Основная ELF-цель и команда вывода размера остаются даже при пустом списке. Неизвестный элемент не добавляет команды; поддержанный bin продолжает добавляться. При смене профиля не должны оставаться команды предыдущего выбора.

Дополнительно проверяется отсутствие созданных ELF/BIN/HEX/MAP/LSS в каталоге сборки: никакая конверсия или линковка не выполняется. Тесты не доказывают корректность форматов, листинга, размеров памяти или CRC, а Arduino backend этим набором не покрывается.

### Пути к пользовательским библиотекам

Пять сценариев `custom-library-*` проверяют custom_libraries от корня проекта, предупреждение и пропуск отсутствующего файла, `_append` в профиле, замену/очистку списка при повторном Configure и сочетание с `link_libraries: [m]`. Проверяются точный порядок LINK_LIBRARIES и генерируемые аргументы Ninja, включая путь `prebuilt/vendor sdk/libbeta.a` с пробелом. Обычное имя m превращается в -lm, но существование и разрешение его символов на этом этапе не проверяются.

Два `.a` в [prebuilt](../../tests/fixtures/project/prebuilt/README.md) содержат только стандартный заголовок ar, без объектных файлов и ABI. Это входные фикстуры для проверки путей; компилятор и архиватор для их создания не запускались. Линковщик также не запускается. Тесты не доказывают пригодность библиотеки для MCU, совместимость ABI или разрешение символов. Семантика Arduino custom libraries отдельна и этими сценариями не проверяется.

### Поиск библиотек Arduino

Пять сценариев `arduino-library-*` проверяют библиотеку с CMake-обёрткой, явное подключение к основной цели и простое добавление цели, предупреждения при отсутствии каталога или CMakeLists.txt, переходы профилей выбранная библиотека → пустой список → выбранная без подключения. Проверяются LINK_LIBRARIES, команды компиляции, передача публичного определения и удаление исходника библиотеки после очистки списка.

[Синтетическая структура ядра](../../tests/fixtures/project/arduino-library-core/README.md) содержит тестовые обёртки библиотек и ссылку на закреплённые исходники ядра. Она не подтверждает совместимость штатных обёрток Arduino: например, EEPROM и IWatchdog в закреплённом Core 2.12.0 требуют CMake 3.21. Минимум фреймворка остаётся 3.19; зависимости могут предъявлять более высокие требования. Собственные обёртки через `arduino.custom_libraries` — отдельный путь с другими требованиями. Прошивки не собираются.

### Пользовательские обёртки Arduino

Пять сценариев `arduino-custom-*` проверяют `arduino.custom_libraries` при пустом `arduino.libraries`. Две пользовательские OBJECT-библиотеки образуют цепочку публичных зависимостей через Arduino::Definitions и Arduino::Core. Оба каталога обёрток называются `driver`: успешная генерация проверяет разные бинарные каталоги для разных относительных путей, но не все возможные коллизии нормализации имён.

Проверяются принадлежность исходников целям, транзитивные определения/include-пути, раздельные флаги C/C++, отсутствие автоматической линковки, предупреждения при отсутствии каталога/CMakeLists.txt и переходы профилей выбранные библиотеки → пустой список → без подключения к основной цели. Обёртки синтетические, по схеме пользовательского проекта с Core/SrcWrapper/периферией; они не реализуют и не проверяют SPI, Wire или HAL. Компиляция, включение объектных файлов при линковке и выполнение прошивки остаются вне этого набора.
