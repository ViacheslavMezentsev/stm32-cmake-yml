# Окружение тестирования

[English](../en/testing.md)

Тестирование использует изолированное Linux-окружение и тестовые проекты CTest.
Существующие проекты с `include(stm32_yml)` не требуют изменений. Тесты вызывают
фреймворк из текущего checkout и проверяют результат Configure/Generate;
компиляция прошивок не выполняется.

## Состав

| Компонент | Закреплённые версии |
| --- | --- |
| Платформа | Linux amd64, Ubuntu 24.04 с фиксированным digest образа |
| Пакеты Ubuntu | Репозитории Ubuntu; установленные версии записываются в образ |
| xPack Arm GCC | 13.3.1-1.1, 14.2.1-1.1, 15.2.1-1.1 |
| CMake | 3.19.8 (минимальная совместимость), 3.28.3 (опорное окружение) |
| Ninja / Mike Farah yq | 1.12.1 / 4.44.3 |
| stm32-cmake | Коммит указан в lock-файле |
| STM32Cube | F1 1.8.7, F4 1.28.3, G4 1.6.3 |
| Arduino Core STM32 / ETL | 2.12.0 / 20.47.1 |

[dependencies.lock.json](../../ci/dependencies.lock.json) содержит SHA-256 архивов
и коммиты исходников. Выбранные подмодули Cube (CMSIS device, HAL и FreeRTOS там,
где это подмодуль) используют gitlinks закреплённых коммитов, а не вершины веток.
Подмодули BSP и прочих middleware не инициализируются. Git-метаданные и лицензии
сохраняются для проверки. Версии пакетов Ubuntu записываются в образе в
`/opt/stm32-yml-ci/packages.txt`.

QEMU **11.0.0**, собираемый из исходников, и Renode запланированы для следующего
этапа эмуляции; в этот образ они не включены. Arduino-проектам по-прежнему нужны
свои CMake-обёртки ядра и библиотек. Образ не содержит копию stm32-cmake-yml.

## Сборка и проверка

Нужен Docker с Linux-контейнерами. Запуск из корня репозитория, одинаково в
PowerShell и Linux shell:

```sh
docker build --platform linux/amd64 -f ci/docker/Dockerfile -t stm32-yml-ci:local .
docker run --rm --network none stm32-yml-ci:local
```

Первая сборка скачивает три toolchain и исходники Cube: потребуется несколько ГБ
диска и время на загрузку. Последующие сборки используют кэш слоёв Docker.
Отдельный ignore-файл Dockerfile передаёт только файлы окружения.
Контрольные суммы проверяются до распаковки. Ошибка установки останавливает сборку.

Команда по умолчанию проверяет версии инструментов, преобразование YAML,
коммиты исходников и наличие необходимых файлов зависимостей. Затем выполняет
конфигурацию маленького C/C++/ASM-проекта для всех шести сочетаний GCC/CMake и
проверяет генерацию файлов Ninja. CMake выполняет собственные проверки
компилятора, но `cmake --build` не вызывается. Это проверка готовности окружения,
**не** поведения фреймворка, линковки прошивки, корректности CRC или симуляции
периферии MCU. Проверка работает без сети.

## Выбор инструментов и подключение рабочей копии

По умолчанию: GCC `14.2.1-1.1`, CMake `3.28.3`. Переменные `GCC_VERSION` и
`CMAKE_VERSION` выбирают установленную версию. Неизвестные и пустые значения
немедленно приводят к ошибке.

```sh
docker run --rm --network none -e GCC_VERSION=13.3.1-1.1 -e CMAKE_VERSION=3.19.8 stm32-yml-ci:local cmake --version
docker run --rm --network none -e GCC_VERSION=15.2.1-1.1 stm32-yml-ci:local arm-none-eabi-gcc --version
```

Открыть shell с текущей рабочей копией, подключённой только для чтения.
Результаты размещайте в `/tmp/build/...` или отдельном writable mount. Linux:

```sh
docker run --rm -it --network none --mount "type=bind,source=$(pwd),target=/workspace,readonly" stm32-yml-ci:local bash
```

PowerShell:

```powershell
docker run --rm -it --network none --mount "type=bind,source=$($PWD.Path),target=/workspace,readonly" stm32-yml-ci:local bash
```

Внутри контейнера:

- Toolchain: `$STM32_TOOLCHAIN_PATH`, выбранные исполняемые файлы также в `PATH`.
- stm32-cmake: `/opt/modules/stm32-cmake`.
- Cube: `/opt/STM32Cube/Repository/STM32Cube_FW_<family>_V<version>`;
  `CMAKE_USER_HOME=/opt` включает существующий механизм поиска фреймворка.
- Arduino Core: `/opt/Arduino_Core_STM32/2.12.0`.
- ETL: `/opt/etl/20.47.1`.
- Проверяемый фреймворк: `/workspace`, подключается вызывающей стороной.

Используйте отдельные build-папки для проекта/профиля/GCC/CMake/типа сборки.
Сохраняйте выбранное окружение при запуске команд: используйте `bash`, а не
login shell, который может сбросить `PATH`. Эти же Docker-команды доступны в
терминале VS Code. Интерактивная отладка и launch-конфигурации добавятся позднее.

## Обновление и CI

Workflow окружения собирает образ и проверяет его без сетевого доступа.
Отдельный workflow `Configure tests` запускается для каждого PR, при push в
`main` и вручную. Он собирает образ один раз и проверяет шесть пар инструментов
в одном задании, продолжая работу после неудачной пары. Оба workflow не публикуют
образы и не собирают прошивки. Отсутствие фильтра по путям позволяет сделать
проверку обязательной для PR без зависания пропущенных запусков в ожидании.

Обновляйте версии и хэши вместе в lock-файле, проверяйте источники upstream,
затем пересобирайте и проверяйте образ. При изменении Ubuntu также обновляйте
digest в Dockerfile, чтобы он совпадал с lock-файлом.
CMake 3.28.3 — фиксированная опорная версия, а не последняя доступная.
Системные библиотеки и Python получают обновления Ubuntu: закреплены инструменты
тестирования и исходники зависимостей, но не каждый пакет ОС и не байты итогового
образа. Доступность сервиса снимков Ubuntu не требуется.

## Проверки конфигурации фреймворка

[tests/cases.json](../../tests/cases.json) описывает 19 сценариев, каждый из
которых запускается на трёх версиях GCC и двух версиях CMake из lock-файла:
**114 выполнений тестов**.

| Область | Проверки |
| --- | --- |
| Значения по умолчанию и зависимости | F411 (BlackPill) и F103 (BluePill), реальные цели CMSIS/HAL, heap/stack по умолчанию, стандарты C/C++ |
| Профили одного MCU | Замена списков, дополнение, замена с последующим дополнением, исходники, внешние профили, приоритет скалярных overrides |
| Флаги языков | Нормализация и раздельное применение флагов/определений C и C++ в `compile_commands.json` |
| Linker | Явный `.ld`, поиск шаблона в `linker_script_dir`, подстановка heap/stack, сохранение READONLY и секции checksum |
| CRC | Наличие/отсутствие сгенерированной post-build команды, аргументы секции и размера Flash |
| Arduino | Пользовательские обёртки ядра и библиотеки, параметры профиля, общие compile definitions, `use_core_main: false` |
| Диагностика | Отсутствующий/некорректный YAML, отсутствие linker/core, неверный размер памяти, HAL без CMSIS, список профилей и предупреждение о неизвестном профиле |

Это небольшие примеры **только для Configure/Generate**, а не готовые прошивки
для плат. Обёртка Arduino использует настоящий исходник закреплённого ядра, но
не описывает полную конфигурацию платы/variant. Её toolchain предоставляет
функцию вывода размера, которую ожидает текущий фреймворк, по аналогии с
toolchain проекта-потребителя. Синтетический linker template проверяет
подстановки и сохранение секций, а не правильность размещения в памяти.
Исполнение CRC, линковка прошивок, периферия, QEMU и Renode остаются за рамками
этапа. При определении компилятора CMake может компилировать собственные пробы.

Положительный сценарий требует успешного завершения CMake, создания Ninja-файла,
кэша и базы команд компиляции, а также совпадения параметров или свойств целей.
Отрицательный сценарий требует и ошибки, и конкретной диагностики: случайная
проблема с компилятором не засчитается как успех. Сохраняется текущее поведение:
неизвестный профиль вызывает предупреждение и продолжение настройки;
`STM32_YML_PROFILE=list` выводит имена и завершается ошибкой. Вывод списка из
внешнего файла и переключение профилей в существующей build-папке пока не
проверяются; каждый сценарий намеренно получает свежий кэш.

Полная матрица запускается из корня репозитория после сборки образа, описанной
выше. PowerShell, в том числе терминал VS Code:

```powershell
New-Item -ItemType Directory -Force build/configure-tests | Out-Null
docker run --rm --network none --mount "type=bind,source=$($PWD.Path),target=/workspace,readonly" --mount "type=bind,source=$($PWD.Path)/build/configure-tests,target=/results" stm32-yml-ci:local python3 /workspace/ci/run_configure_tests.py --output /results
```

Linux:

```sh
mkdir -p build/configure-tests
docker run --rm --network none --user "$(id -u):$(id -g)" --mount "type=bind,source=$PWD,target=/workspace,readonly" --mount "type=bind,source=$PWD/build/configure-tests,target=/results" stm32-yml-ci:local python3 /workspace/ci/run_configure_tests.py --output /results
```

Для одной пары инструментов откройте shell контейнера с этими двумя mount и
при необходимости `-e GCC_VERSION=... -e CMAKE_VERSION=...`, затем выполните:

```sh
cmake -S /workspace/tests -B /results/single -G Ninja
cd /results/single
ctest --output-on-failure -j 4
ctest --output-on-failure -R '^configure.profile-'
```

Используйте отдельный каталог `single` для каждой пары. Вариант с `cd` совместим
с CMake 3.19. Корневой `CMakeLists.txt` и presets для проектов-потребителей не
добавляются; точка входа тестов находится в `tests/`.

В выходной папке сохраняются `summary.json`, логи CTest и для каждого сценария:
`configure.log`, копия исходников, сгенерированные файлы и наблюдаемые свойства.
Повторные запуски сохраняют отдельные папки сценариев для диагностики и занимают
место до удаления сгенерированных результатов. GitHub сохраняет выбранные файлы
в артефакте `configure-diagnostics` на 14 дней, в том числе при падении тестов.
Симлинки на ядро и исходники зависимостей в артефакт не включаются.

Для нового сценария дополните `tests/cases.json` и при необходимости тестовые
файлы. Проверяйте наблюдаемый результат, не копируйте логику фреймворка в тесты.
Перед изменением поведения в следующем PR добавляйте регрессионный сценарий.
Имена тестов должны оставаться уникальными.
