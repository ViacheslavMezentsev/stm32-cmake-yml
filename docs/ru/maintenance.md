# Сопровождение проекта и справочника

[Документация](index.md) → Сопровождение · [English](../en/maintenance.md)

Markdown-страницы редактируются непосредственно. Генератор документации не
требуется; `docs/reference-index.json` — индекс навигации и покрытия, не YAML
Schema и не второй набор defaults. Карточки RU/EN — общая спецификация для людей
и агентов. Навык ссылается на них, а не копирует таблицы.

## Порядок работы с проектом

Раздел — общая инструкция для людей и ИИ-агентов; точка входа — [AGENTS.md](../../AGENTS.md).
Здесь не повторяются требования: их источник — ТЗ, а текущая ревизия указана
в его реквизитах.

**Порядок ознакомления**

1. [README](../../README.md) — назначение фреймворка и границы подхода.
2. Этот раздел и разделы ниже о ветках, CI и справочнике.
3. [TODO.md](../../TODO.md) — текущая ветка, слитые изменения и ближайшие шаги.
4. [ТЗ](../TECHNICAL_SPECIFICATION.md): история ревизий, блок изменений последней
   ревизии, открытые вопросы (раздел 10) и доработки версии (приложение E).
5. Для конкретной задачи — [errata](errata/index.md), карточки
   [справочника](reference/0.9.2/index.md), [тестирование](testing.md),
   [прошивочные тесты](firmware-testing.md) и [CHANGELOG](../../CHANGELOG.md).

**Рабочий цикл**

1. Ветка `<агент>/<задача>` от актуального main (раздел «Ветки без PR»). Решение
   частой проблемы записывается в [памятку](HOWTO.md) в том же коммите.
2. Изменение поведения — по п. 7.4 ТЗ: регрессия, карточка `CFG-*` и индекс,
   запись в обоих файлах истории изменений ([RU](../../CHANGELOG.md),
   [EN](../../CHANGELOG.en.md)) в формате раздела версии, новая ревизия ТЗ.
   Ссылки на пункты ТЗ из кода и тестов — по приложению D (`# ТЗ 4.15.9`).
3. Локальные проверки затронутых уровней L0–L5 (п. 8.1 ТЗ; команды — приложение F
   ТЗ, [testing.md](testing.md), [firmware-testing.md](firmware-testing.md));
   документация — `python ci/check_reference.py`.
4. Коммит, push ветки, зелёные Docs и Configure для последнего коммита, слияние
   в main перемоткой (`git land`, [памятка](HOWTO.md#git-рабочий-цикл-без-pr)).
   Перед выпуском версии все проверки повторяются локально на итоговом коммите
   ветки выпуска (п. 8.6.1, 8.8.7 ТЗ).
5. Запись ветки, коммита и статуса в TODO.md.

**Выпуск версии** (п. 8.6.1 ТЗ):

1. `STM32_CMAKE_YML_VERSION` в `stm32_yml.cmake` и `stm32_cmake_yml_version` в
   тестовых YAML и примерах документации.
2. Раздел `## [X.Y.Z] - дата` в CHANGELOG.md и CHANGELOG.en.md.
3. Ревизия ТЗ «к выпуску» с обновлённым приложением E.
4. Все проверки L0–L5 локально на итоговом коммите ветки выпуска и зелёный CI
   для того же коммита.
5. Ручной прогон Firmware на ветке выпуска, слияние в main (`git land`), затем тег
   `vX.Y.Z` на новом HEAD main.
6. Статусы errata `released` с версией в обеих локализациях и в
   `docs/reference-index.json`; запись в TODO.md.

**ТЗ**

- Ведётся по навыку [embedded-tech-spec](https://github.com/ViacheslavMezentsev/demo-stm32-skills/tree/main/embedded-tech-spec):
  каждая правка — новая ревизия с пометками `(р.X.Y)`, блоком изменений и
  обновлением вопросов, тест-кейсов, матрицы и приложений.
- После правки: `python3 check_spec.py docs/TECHNICAL_SPECIFICATION.md --strict`
  (скрипт `scripts/check_spec.py` навыка) — без ошибок и предупреждений.
- Ответ заказчика переносится в требование, а не только в таблицу вопросов.
  Проверенное и непроверенное различаются явно.
- Копии ТЗ вне репозитория не ведутся: читайте файл в рабочей ветке.

**Практические правила**

- Сообщения коммитов — Conventional Commits на английском (`ci:`, `docs:`, `test:`,
  `fix:`) с пояснением «что и почему»; без ссылок на сессии агентов.
- Файлы `ci/**`, `tests/**`, `tools/**`, `.github/workflows/**` хранятся с LF
  (`.gitattributes`); остальные в рабочей копии Windows могут иметь CRLF —
  сохраняйте окончания строк редактируемого файла.
- Бинарные архивы (`tools/qemu`) закрепляются SHA-256 в lock-файлах; меняются
  только вместе с контрольной суммой.

## Изменение опции

1. Установить исходный commit/version и проверить реализацию, в том числе кэш.
2. Уточнить ожидаемый контракт; наблюдаемую ошибку записать отдельно в errata.
3. Обновить карточки RU/EN с одним стабильным `CFG-*` ID и индекс.
4. Связать фактически существующие тесты. Не объявлять проверенным весь контракт
   по одному Configure-тесту. Если проверки нет, оставить `tests: []`.
5. При изменении поведения добавить регрессию и запись совместимости/changelog.
   Не исправлять runtime-код незаметно в документационном PR.
6. Выполнить `python ci/check_reference.py`.

`since: null` означает, что история появления не установлена; `verified_in`
означает присутствие в проверенной базе. Не заменяйте одно другим.
При добавлении новой YAML-опции одновременно добавьте запись в индекс и карточку;
проверка индекса не доказывает отсутствие недокументированных динамических ключей.

## Шаблон карточки

```text
CFG-OPTION-ID / точное имя YAML
Назначение и поддерживаемое ожидаемое поведение
Тип, допустимые значения и условные defaults
Отсутствие / null / false / 0 / []
Приоритет, профиль, override и повторный Configure
Backend, зависимости, база путей и стадия применения
Пример YAML; связанные опции
Совместимость: проверенный commit, изменения, неизвестная история
Реализация; тесты и пределы покрытия; ссылки E*
```

## Шаблон errata

```text
E<number> / название
Затронутые опции и точная проверенная база
Условия и минимальное воспроизведение
Ожидаемый результат / фактический результат / влияние
Обход и его ограничения
Подтверждение: воспроизведено или source-confirmed
Статус: open / fix-prepared / merged / released
Commit исправления, PR, версия релиза (если подтверждены)
Регрессионный тест (если существует)
```

Идентификаторы не переиспользуются. Исправленные записи не удаляются. Дата аудита
ограничивает утверждения о статусе: после слияния обновите обе локализации и индекс;
слияние само по себе не означает выпуск версии. Непроверенные подозрения ведите
в обсуждении/issue до подтверждения, не смешивайте с подтверждёнными errata.

## Проверки CI

Workflow `Docs` (`ci/check_reference.py`) проверяет доступность локальных ссылок новых страниц,
RU/EN anchors, уникальность ключей/ID, ссылки на существующие тесты и взаимную
согласованность списка errata. Она не проверяет внешнюю сеть и не доказывает
семантическую правильность текста. Новые примеры, утверждения об ошибках и
изменения контрактов требуют отдельной проверки поведения.

## Основание ожидаемого поведения

Не выводите обещание поддержки из одного примера, regex или факта ошибки.
Сначала сопоставьте пользовательский контракт, реализацию и назначение функции.
Если ожидаемое поведение неоднозначно, уточните его у автора до объявления дефекта
или изменения реализации. Неподдерживаемый вход не означает баг.
Статус `closed-by-design` сохраняет ошибочно классифицированную запись для истории
ссылок и не означает, что было выпущено исправление.

Страницы docs/ru/status.md и docs/en/status.md содержат проверяемый объём набора, а не число прошедших тестов. При
изменении `tests/cases.json` или матрицы в lock-файле обновляйте блок
`configure-counts`: валидатор сверяет число сценариев, пар инструментов и их
произведение. Статусы workflow на main показываются отдельными бейджами.

## Ветки без PR

Изменения выполняются в ветке `<агент>/<задача>` от актуального main. Префикс — имя
агента или участника, создающего ветку (`claude/`, `codex/`, `gemini/`, `dev/`, …).
Для нового префикса добавьте `<префикс>/**` в `on.push.branches` workflow, иначе push
ветки не запустит CI.

После локальных проверок ветка отправляется на GitHub; нужны зелёные Docs и Configure
для её последнего коммита. Затем владелец сливает её в main перемоткой (`git land`):
merge-коммит не создаётся, ветка удаляется. Если ветка отстала от main, её переносят
на свежий main (`git rebase -S origin/main`) и повторяют затронутые проверки. Команды,
псевдоним `git land`, уборка веток и типичные ошибки — в [памятке](HOWTO.md#git-рабочий-цикл-без-pr).

- PR не используются; ссылки на PR #1…#46 сохраняются как история.
- Коммиты в main подписаны (Verified). Агент вносит правки в рабочую копию владельца,
  а коммитит их владелец из Windows своим ключом; готовые неподписанные коммиты агента
  переподписываются перед push (`git rebase -S origin/main`), поэтому в документации
  не ссылаются на хэши коммитов той же неслитой ветки. Подробности — в
  [памятке](HOWTO.md#схемы-работы-агентов).
- Push, теги и релизы выполняет владелец. Force push в main и чужие ветки запрещён;
  `--force-with-lease` допустим только для своей неслитой ветки.
- Не считайте проверки старого коммита проверками новых изменений. В TODO фиксируются
  ветка и статус.

## Кэш Docker-слоёв

Образ `ci/emulation` (QEMU из архива [tools/qemu](../../tools/qemu/README.md), Renode) собирается через BuildKit с кэшем
слоёв GitHub Actions (`type=gha`, область `stm32-yml-emulation`). Ключ слоя —
инструкция Dockerfile и содержимое скопированных файлов, поэтому изменение
lock-файла, скрипта установки или Dockerfile пересобирает этот слой и последующие.
Загрузки закреплены SHA-256, поэтому кэш не меняет состав образа.

Firmware читает и пополняет кэш. Emulation environment собирает образ с нуля
(`no-cache`) и только записывает свежий кэш: он подтверждает, что закреплённые
загрузки доступны и собираются. Кэш ветки виден ей и её потомкам; ветки читают кэш
main, main кэш веток не читает. Неиспользуемые записи удаляются через 7 дней;
при промахе образ собирается с нуля, как раньше.

Образ `ci/docker` (около 8 ГБ: три GCC, два CMake, исходники Cube/Arduino/ETL)
не кэшируется. Замеры ветки `claude/docker-image-cache`:

| Образ | Без кэша | Сборка и запись кэша | Из кэша |
| --- | ---: | ---: | ---: |
| emulation | 3:08 | 6:16 | 0:12 |
| ci/docker | 2:55–3:01 | 9:02–10:37 | 2:35–2:38 |

Для компиляторов скачивание кэша и загрузка 8 ГБ в Docker почти равны сборке
из быстрых релизных загрузок, а каждая запись кэша добавляет 6–7 минут.
Firmware со всеми образами из кэша занял 5:34 вместо 10:04. Позже компиляция QEMU
в образе заменена готовым архивом [tools/qemu](../../tools/qemu/README.md), поэтому
и сборка образа эмуляторов без кэша больше не компилирует QEMU.

## Ускорение CI: рассмотренные варианты

Принято (по замерам job на GitHub): Renode в одном процессе на пару (3:42 → 0:33),
кэш слоёв только для образа эмуляторов, готовый QEMU в `tools/qemu`, параллельная
установка зависимостей и Cube без `Projects`/`Utilities`. Сборка образа
компиляторов сократилась с ~2:45 до 1:09–1:29; Configure занимает около 4:47,
Firmware — 4:39 (ветка `claude/faster-ci-image`, `f3f1309`).

Внутри job резерв мал: `ctest -j 4` и `cmake --build --parallel 4` уже занимают
4 ядра раннера. Дальнейший вариант — **не принят**, оставлен на будущее:

- Разнести пары GCC/CMake по job (`strategy.matrix`): 6 job Configure и 6 job
  Firmware по одной паре, итоговые job `configure` и `smoke` сверяют полноту
  матрицы и собирают `matrix-summary.json` и бейдж; матрицу строит job `pairs`
  из `ci/dependencies.lock.json`. Всего 15 job вместо 2.
- Оценка: Configure ~2:00, Firmware ~2:45 вместо ~4:45. Нижняя граница — сборка
  образа в каждом job.
- Цена: время раннеров на push растёт с ~9,5 до ~25 минут (образ собирается в
  12 job), нужны выбор пары в `run_configure_tests.py` и `firmware_matrix.py`,
  склейка отчётов и перестройка workflow и бейджа.

Имеет смысл вернуться к варианту, если матрица вырастет (новые GCC/CMake или
семейства) или время push станет узким местом. Прежде стоит уменьшить сам образ
компиляторов, так как его сборка повторяется в каждом job.

## Схема проверок на GitHub

На время разработки 0.10 (п. 8.5.2 ТЗ) полная матрица прошивок не запускается
на каждый push:

| Workflow | Когда запускается |
| --- | --- |
| Docs | каждый push |
| Configure (6 пар, 1026 запусков, ~6 мин) | каждый push, кроме push без входных данных (ниже) |
| CI environment, Emulation environment | push с изменением файлов своего образа |
| Firmware (570 сборок, 948 запусков, ~24 мин) | вручную (Actions → Firmware → Run workflow) и на теге `v*` |

Firmware запускают вручную на границах этапов и перед выпуском; бейдж
`Builds (Checks)` обновляет только ручной запуск на main. Полный прогон L0–L5
локально выполняется в конце каждого этапа и перед выпуском.

## Push только с документацией

Если push меняет только `.md` на любой глубине, запускается Docs, а Configure,
CI environment и Emulation environment пропускаются. Configure также не
запускается при изменении только `docs/reference-index.json`, `.github/FUNDING.yml`,
`.github/ISSUE_TEMPLATE/` или `LICENSE`. Смешанный push с Markdown и кодом
по-прежнему запускает соответствующие workflow. CI environment и Emulation
environment сохраняют включающие фильтры путей; исключение Markdown стоит последним.
Ручной `workflow_dispatch` остаётся доступен. Изменение самого workflow/фильтров
не считается правкой только документации.

Счётчик Firmware сохраняет последнюю успешно проверенную ревизию при пропуске CI
для документации и не утверждает, что новый MD-коммит был собран. Бейджи workflow
в README используют Shields.io `flat-square` без логотипа; генерируемый SVG
`Builds (Checks)` имеет такую же прямоугольную форму. Числа вычисляются из
проверенных отчётов, вручную в README не задаются.

[Фильтры путей GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushpull_requestpull_request_targetpathspaths-ignore)
описывают смешанные изменения, порядок шаблонов и пропущенные обязательные проверки.
Если защита ветки требует пропущенный workflow, эту политику нужно согласовать
с MD-only слияниями. Настройки защиты этой веткой не изменяются.
