# Метод CRC32 и разметка образа

[Документация](index.md) · [English](../en/crc-methods.md) · [Опции CRC](reference/0.9.2/postbuild.md#crc-method)

Для 0.10.1 `crc_method: auto` сохраняет существующий расчёт и запись CRC.
Метод объединяет алгоритм, защищаемый диапазон и размещение результата;
`crc_algorithm` задаёт только алгоритм, `crc_section_name` — только имя секции.
`none`, null и пустота у метода означают auto. Отключение — `crc_enable: false`.

## Алгоритм

| Свойство | Значение |
| --- | --- |
| Полином | `0x04C11DB7` |
| Начальный регистр | `0xFFFFFFFF` перед каждым независимым расчётом |
| Вход | 32-битные слова; четыре байта образа собираются в слово little-endian |
| Обработка | Старший бит слова первым, без отражения входа/выхода |
| Финальный XOR | Нет |
| Записанная CRC | Четыре байта little-endian |

Это алгоритм `STM32_HW_DEFAULT`, а не стандартный CRC32 из zlib.
Пример: байты `78 56 34 12` образуют слово `0x12345678`; CRC равна
`0xDF8A8A2B`, а в образ записываются байты `2B 8A 8A DF`.
Для слова `0` результат `0xC704DD7B`; для слов `0x12345678`, `0x9ABCDEF0` —
`0x7D24A31B`. Эти векторы проверяются на хосте и компилятором тестовой прошивки.

Аппаратный блок должен считать именно эти слова с указанными параметрами.
Если настройки доступны, нужны стандартный полином и начальное значение,
отключённая инверсия/отражение и ввод словами. Тактирование блока и его
инициализацию обеспечивает приложение. Перед независимым расчётом состояние
CRC сбрасывают; в API с аргументом длины в словах передают размер в байтах / 4.
Симуляторные тесты используют программный эквивалент и не проверяют периферию CRC.

## Секции и поле длины

Рекомендуемая разметка для auto:

```text
начало образа = __checksum_start
  таблица векторов
  выравнивание 4 → LONG(__checksum_size)
  код, константы, init arrays и другие данные FLASH
  загрузочная копия .data (VMA в RAM, LMA во FLASH)
  метаданные, включая .fw_version, если она нужна
  выравнивание 4
конец защищаемого диапазона = __checksum_end
  четыре байта CRC в crc_section_name
конец образа = __checksum_end + 4
```

Это порядок адресов **загрузки LMA**, а не только порядок VMA или строк `.ld`.
Секция с CRC должна идти после всех секций, занимающих место во FLASH, включая
`.data` с `AT> FLASH`. `.bss` без содержимого не входит в образ.
Другие загружаемые секции после CRC нарушают эту разметку.

Фрагменты пользовательского linker script (не полный скрипт):

```ld
.isr_vector :
{
  . = ALIGN(4);
  __checksum_start = .;
  KEEP(*(.isr_vector))
  . = ALIGN(4);
  __checksum_length_field = .;
  LONG(__checksum_size)
} >FLASH

/* Здесь все остальные секции с FLASH LMA, в том числе .data AT> FLASH. */
.checksum :
{
  . = ALIGN(4);
  __checksum_end = .;
  LONG(0)
} >FLASH
__checksum_size = __checksum_end - __checksum_start;
```

`__checksum_length_field` — удобная метка примера и тестов, фреймворк её не требует.
Поле содержит именно **значение** `__checksum_size`, а не адрес поля или заглушку.
Само поле длины входит в защищаемый диапазон. Размер исключает четыре байта CRC;
полный размер такого образа — `__checksum_size + 4`.

Универсального смещения поля от начала прошивки нет: длина таблицы векторов
зависит от MCU и startup. Для внутрифирменного формата договоритесь о поиске
поля явно; в тестах его адрес берётся из символа ELF. Дополнительное выравнивание
для кода, например ALIGN(16), размещайте **после** LONG. В тестовых скриптах так
материализуется заполнение перед кодом FreeRTOS; это не требование алгоритма CRC.

## Какой диапазон считает сборка

Скрипт читает ELF, исключает `crc_section_name` и выбирает секции с содержимым,
у которых LMA находится в регионе FLASH итогового `.ld`. Диапазон — от минимального
LMA до конца последней выбранной секции; промежутки заполняются `0xFF`.
Неполное последнее слово также дополняется `0xFF`. Для описанной разметки диапазон
должен совпадать с `[__checksum_start, __checksum_end)` и быть кратным четырём.

Линкерные символы сами по себе не управляют диапазоном Python-скрипта.
Проверьте карту памяти, секции ELF, `*_no_crc.bin` и итоговый BIN: содержимое
промежутков при чтении из FLASH должно совпадать с байтами, участвовавшими в расчёте.
Пустоты загрузочного образа и заполнение линкером не всегда эквивалентны.

`crc_method: auto` не переставляет секции, не добавляет поле длины и не проверяет
весь контракт разметки. Напоминание Configure не является результатом проверки ELF.
Существующие проекты без поля длины продолжают собираться; поле — часть формата
образа, которую задаёт пользователь. Произвольное имя секции допустимо, если оно
одинаково в YAML и `.ld`; примеры для него проверены отдельно на этапе post-build.

## Чтение и две проверки

Для описанной разметки из кода доступны адреса секций и поле длины:

```cpp
extern "C" uint32_t __checksum_start[], __checksum_end[];
extern "C" uint32_t __checksum_length_field[];

const uintptr_t begin = reinterpret_cast<uintptr_t>(__checksum_start);
const uintptr_t end = reinterpret_cast<uintptr_t>(__checksum_end);
const uint32_t length = __checksum_length_field[0];
const uint32_t stored = __checksum_end[0];
// Сначала проверить границы, выравнивание и length == end - begin.
```

`__checksum_size` — абсолютный символ линкера, а не переменная в памяти.
Если объявить его как внешний символ, его числовое значение получают через адрес;
разыменовывать адрес `__checksum_size` для чтения длины нельзя.
Для принятого по каналу образа проверяют границы буфера до чтения полей; размер
из недоверенного поля не должен задавать неограниченный диапазон чтения.

Есть два эквивалентных критерия при согласованном диапазоне:

1. CRC по `length / 4` словам с начальным `0xFFFFFFFF` равна `stored`.
2. CRC по тем же словам **и следующему слову stored**, с тем же начальным
   значением и алгоритмом, равна нулю.

Второй критерий следует из шага алгоритма: после XOR текущего регистра со словом,
равным этому регистру, остаётся ноль. Записанные little-endian байты необходимо
снова прочитать тем же 32-битным словом. Сравнение с нулём не переносится автоматически
на другие CRC-алгоритмы, порядок байтов или настройки аппаратного блока.
CRC обнаруживает повреждения, но не является криптографической подписью.

## Покрытие

В существующих semihosting-прошивках для F0/F1/F4/G4/F7 (семь целей) поле длины
добавлено в `.ld` и `.ld.in`. Хост независимо проверяет значение поля, расположение
CRC, ELF/BIN и остаток; прошивка проверяет длину, рассчитанную CRC и нулевой остаток
программно. Метаданные сравниваются при запуске QEMU/Renode. Порча `.fw_version`
должна давать ненулевой остаток и прежний управляемый отказ.
Хостовая регрессия отдельно отклоняет неверную длину даже после пересчёта CRC.

Число сборок и запусков не увеличивается. H5/H7 build-only/native сценарии не
получают это новое поле: их форматы и прежние проверки остаются отдельными.
Аппаратный блок CRC, периферия и работа загрузчика этим набором не проверяются.
