Это объём набора, а не счётчик успешных запусков. CI сверяет число с
[manifest](../../tests/cases.json) и [lock-файлом](../../ci/dependencies.lock.json).
Матрица: xPack GCC 13.3.1-1.1, 14.2.1-1.1, 15.2.1-1.1 × CMake 3.21.7 и 3.28.3.

Проверяются Configure/Generate, профили, приоритеты настроек, IOC, компоненты,
исходники и диагностика. Есть сценарии F0/F1/F3/F4/F7/G4/H5/H7 (в том числе выбор ядра MCU), таблица портов
FreeRTOS для C0/U0/L5/U5/WL, bare metal и Arduino;
набор не покрывает все сочетания MCU и параметров. Ожидаемые ошибки и известные
отклонения проверяются отдельно. Успешный Configure не доказывает успешную линковку
или работоспособность прошивки. [Состав и команды](testing.md).

## Сборка и исполнение

Отдельная матрица содержит **618 сборок, 336 запусков QEMU и 612 запусков Renode**: тринадцать профилей на цели F103, F030, F411, F401, G431, G474 и F746 (G4 и F7 — только Renode)
четыре H7/H5 (только Renode) и восемь прошивок режима Arduino `native` (только сборка) на шести парах инструментов и по одной повреждённой копии ELF на цель и пару. Проверяются структура
ELF, начальные данные, C++-конструктор, метаданные, программная CRC и управляемый
выход; отрицательные сценарии различают ошибку прошивки и таймаут.

QEMU 11.0.0 проверяет только F103 и F030 на `netduino2` (Cortex-M3/F205),
F411 и F401 — на `netduinoplus2` (Cortex-M4F/F405). Это проверка выбранного
пути запуска и содержимого образа: например, F030 запускается на M3 вместо M0.
Периферия исходного MCU таким запуском не проверяется.

Renode проверяет F103, F030, F411/F401, G431/G474, F746, H743 и H503/H563
на минимальных моделях CPU/NVIC/SysTick/памяти соответствующих семейств,
с заглушками отдельных регистров и адаптером semihosting exit. G4, F7, H7 и H5
в QEMU не запускаются. Arduino `native` пока проверяется только сборкой:
для запуска нужны модели RCC/PWR. [Контракт прошивок](firmware-testing.md) ·
[Окружение и модели по семействам](emulation.md).

## Документация и дальнейшая работа

Валидатор проверяет ссылки, двуязычные карточки опций, errata и привязки к тестам.
Сопоставление опции с тестом обозначает описанное покрытие, не доказательство всех
возможных вариантов использования. [Машиночитаемый индекс](../reference-index.json).

[Errata](errata/index.md) сохраняет ограничения и обходы; для E004 (выбор алгоритма CRC),
E006 (ошибки CRC), E007 (external FreeRTOS) и E008 (языковые параметры только из профиля),
как и для E001 и E002, исправление вошло в 0.9.3 ([история изменений](../../CHANGELOG.md)).
[TODO](../../TODO.md) содержит план и историю этапов; [правила сопровождения](maintenance.md)
описывают обновление документации и проверок. Публичные пути подключения
фреймворка сохраняются; тестирование добавляется без обязательной перестройки проектов.

## Бейдж подтверждённых сборок

Бейдж `Builds (Checks)` в README показывает число собранных конфигураций и выполненных проверок
последнего успешного прогона Firmware на main. Сейчас полный прогон даёт
`Builds (Checks): 618 (948)`. Ожидаемые ошибка, таймаут и отказ CRC считаются успешными
проверками их контрактов; это не 948 нормально завершившихся прошивок и не 618 разных MCU.
Сборки считаются один раз; проверки QEMU и Renode суммируются (336 + 612).

Значения вычисляются из полных согласованных build/QEMU/Renode-отчётов. Проверяются SHA
чистого checkout, состав матрицы, результаты и метаданные. Ветки codex создают
артефакт для просмотра, но не обновляют публичный бейдж. После успешного main
отдельная задача с contents: write публикует SVG и JSON в служебную ветку
ci-badges; исходники и main не изменяются. Дополнительный PAT или Pages не нужны.

При ошибке/отмене остаётся последний успешный результат; текущий статус смотрите
на соседнем бейдже Firmware. Клик по счётчику открывает JSON с SHA, временем и
ссылкой на прогон. Кэш GitHub может задерживать обновление картинки. До первого
успешного main с этим workflow картинка ещё недоступна. Защита веток должна
разрешать GITHUB_TOKEN запись в ci-badges. Если main уже ушёл вперёд, старый
прогон не публикуется.

[E008](errata/E008.md) описывает языковые параметры только из профиля; в 0.9.3 она исправлена, обход удалён, библиотечные профили прошивок работают без корневых ключей.

Все четыре бейджа README отображаются через [Shields endpoints](https://shields.io/badges/endpoint-badge): одинаковые шрифт, высота 20 px и отступы. Зелёный PASS и счётчик используют #238636, как кнопка Code на приложенном изображении GitHub. Ошибки отображаются как красный FAIL; отмена — CANCEL, пропуск — SKIP, отсутствие результата — N/A.

Статусные бейджи показывают последний **завершённый** запуск соответствующего workflow на main. Лёгкий workflow Badges обновляет JSON после завершения Configure/Firmware/Docs; текущий выполняющийся запуск смотрите по ссылке бейджа. counts.json получает только проверенный счётчик последнего успешного Firmware. Сведения о SHA и ссылках статусных запусков сохраняются в workflow-status-report.json. Обе публикации используют общую очередь ci-badges и сохраняют файлы друг друга. Дополнительный PAT не требуется.
