# Сборка прошивки и тесты QEMU/Renode

[Документация](index.md) · [English](../en/firmware-testing.md) · [Окружение](emulation.md)

Первый тест адаптирует [пример автора 02-semihosting для F1](../../tests/firmware/semihosting/README.md).
Он отделён от 115 configure-сценариев: **60 сборок, 66 запусков QEMU и 66 запусков Renode**:
десять профилей и повреждённая копия для каждой пары инструментов; три версии xPack GCC × два CMake из
[lock-файла](../../ci/dependencies.lock.json), CubeF1 1.8.7, QEMU 11.0.0.
Локально проверен также Windows QEMU 11.1.0; CI использует закреплённый образ.

## Контракт

После сборки нужны непустые ELF/BIN/HEX/MAP/LSS. Проверка ELF контролирует ELF32 ARM,
согласованность Thumb reset-вектора и точки входа, выравнивание начального стека
в 20 КиБ RAM и размещение загружаемых сегментов в пределах FLASH/RAM F103C8
(64/20 КиБ), включая LMA .data. Вывод readelf сохраняется. Это не полная проверка
корректности любого linker script.

| Профиль | Ожидаемое выполнение |
| --- | --- |
| success | Вывод компилятора/цели/машины/ядра, TEST_RESULT=PASS, код 0 |
| failure | Тот же стартовый вывод, TEST_RESULT=FAIL, код 1 |
| hang | Стартовый вывод без маркера результата, таймаут через 5 секунд |
| bare / bareTemplate | Свой startup, без CMSIS/HAL, TEST_RESULT=PASS, код 0 |
| cmsis / cmsisTemplate | Startup CMSIS, без HAL, TEST_RESULT=PASS, код 0 |
| cmsisLibrary / cmsisEtl | C/C++-библиотека и опционально ETL, TEST_RESULT=PASS, код 0 |
| arduinoString | Arduino String со своим main/startup, TEST_RESULT=PASS, код 0 |

Обычные запуски ограничены 15 секундами. Зависание до вывода метаданных, авария,
отсутствующий маркер, неверный код выхода или противоречивые маркеры проваливают
набор. Намеренная ошибка и таймаут — успешные проверки тестового runner, а не
игнорирование сбоев. Сохраняются stdout/stderr, команды, коды и версия эмулятора.
GDB и GUI не запускаются. SYS_EXIT_EXTENDED получает блок причины/статуса;
Вывод SYS_WRITE0 выполняется сразу. Версия GCC сравнивается с манифестом сборки.
Версии CMSIS Core/Device, HAL и фреймворка сравниваются с проверенным
эталоном expected-metadata.json для закреплённых зависимостей.

## Локальный запуск

Сначала собрать [образ компиляторов](testing.md) и [образ эмуляторов](emulation.md).
Команды ниже используют Linux shell и пути; в PowerShell нужны соответствующие
абсолютные пути bind mount. Исходники подключаются только для чтения.

```sh
mkdir -p build/firmware-smoke build/firmware-qemu
docker run --rm --network none \
  -v "$PWD:/workspace:ro" -v "$PWD/build/firmware-smoke:/results" \
  stm32-yml-ci:local python3 /workspace/ci/firmware_matrix.py build --output /results
docker run --rm --network none -v "$PWD:/workspace:ro" -v "$PWD/build/firmware-qemu:/results" \
  stm32-yml-emulation:local python3 /workspace/ci/firmware_matrix.py run \
  --build /workspace/build/firmware-smoke --output /results
```

Готовые ELF можно запустить локальным QEMU в Windows:

```powershell
python ci/firmware_matrix.py run --build build/firmware-smoke --output build/firmware-qemu-windows
python -m unittest discover -s tests -p "test_firmware*.py"
```

`--qemu` задаёт путь к программе. Сборки используют новые каталоги, манифест
сбрасывается в начале; неудачная сборка не подхватит старый успешный манифест.
[Workflow](../../.github/workflows/firmware.yml) собирает оба образа и сохраняет
артефакты/логи на 14 дней. Оба симулятора используют одни ELF. Запуск на netduino2 с F205 не
подтверждает поддержку периферии или модели тактирования F1.

## Изоляция матрицы и совместимость

Матрица читается из общего lock-файла зависимостей, без дублирования версий в YAML.
Образы собираются один раз; пары инструментов запускаются последовательно с
отдельными каталогами сборки/логов. Для каждой пары проверяются фактические версии
GCC/CMake и все десять профилей. Ошибка не останавливает сбор результатов остальных
пар, но любая неудачная пара даёт ненулевой результат матрицы. Выбор запусков
определяется текущим lock-файлом, а не случайно оставшимися манифестами. Сводный
отчёт — matrix-summary.json, отчёты пары — build-summary.json и qemu-summary.json.

Тестовый пример использует C11 и C++17. CMake 3.19 отвергает C_STANDARD=17 даже
при поддержке C17 компилятором: это значение появилось в CMake 3.21. C-файлам
примера C17 не требуется. Изменена совместимость тестового примера, а не фреймворк.
Для одной пары сохранены build_firmware_smoke.py/run_qemu_smoke.py; использовать
отдельный каталог результатов.

## Метаданные и начальное состояние памяти

Каждый профиль выводит PROFILE, CMAKE, FRAMEWORK, GIT_REVISION и GIT_DIRTY.
Заголовок генерируется из фактической конфигурации CMake; builder сохраняет Git HEAD
и признак изменений рабочего дерева. HEAD с dirty-флагом не является хешем
содержимого незакоммиченных изменений. Дата/время остаются диагностическими полями.
Отсутствие поля, неверное значение или повтор поля метаданных проваливают запуск,
включая профили намеренной ошибки и таймаута. Старые манифесты без метаданных
требуют повторной сборки.

При входе в main, до настройки HAL, читаются три volatile-переменные по четыре
байта: инициализированная .data = 0x12345678, .bss = 0 и значение, установленное
C++-конструктором, = 0xC0DEC0DE. Несовпадение завершает прошивку кодом 2 до обычной
логики success/failure/hang. Builder проверяет типы D/B и размеры символов через
nm, сохраняет адреса; runner сравнивает их с адресами, напечатанными прошивкой.
Значения переменных дополнительно сравниваются с проверенным эталоном.

Проверяется наблюдаемое начальное состояние памяти и выполнение конструктора.
Нулевая .bss сама по себе не доказывает работу цикла очистки startup: RAM эмулятора
может изначально содержать нули. При разработке в копии одного ELF изменены только
загрузочные байты переменной .data: прошивка выдала FAIL и код 2, runner отверг
запуск. Этот дополнительный эксперимент с .data не входит в регулярную матрицу CI. Исходный demo не изменяется.

## CRC загруженной прошивки

Тестовый STM32F103C8_FLASH.ld располагает загрузочный образ .data и четырёхбайтовую
запись .fw_version перед .checksum. Запись содержит 0x00090200 (формат теста для
0.9.2), сохраняется через KEEP. Фиксированная разметка 64/20 KiB не является
универсальным шаблоном линкера. Символы startup, heap и stack сохранены.

Фреймворк внедряет CRC STM32_HW_DEFAULT. Независимый расчёт на машине сборки и
расчёт C++ внутри прошивки используют полином 0x04C11DB7, начальное 0xFFFFFFFF,
32-битные слова little-endian, без отражений и финального XOR. Три предоставленных
вектора проверяются в Python и static_assert. Диапазон начинается с 0x08000000
и заканчивается перед словом CRC; границы кратны четырём.

Builder отвергает разрывы/перекрытия загрузочных сегментов FLASH, CRC не в конце,
неверное положение .data/.fw_version, неправильную внедрённую CRC и различия BIN/ELF.
Прошивка печатает CRC_START, CRC_END, CRC_STORED, CRC_COMPUTED и CRC_RESULT;
все пять полей должны точно совпасть с манифестом, включая failure/hang.

Для каждой пары инструментов в копии success ELF изменяется один бит .fw_version.
Код, начальные данные и внедрённая CRC остаются прежними. Производный отрицательный сценарий,
crc-corrupt, обязан выдать CRC_RESULT=FAIL и TEST_RESULT=FAIL и завершиться кодом 3.
Авария или таймаут не засчитываются. Это шесть дополнительных запусков без новых
компиляций: 60 сборок, 66 запусков на каждом симуляторе. Отчёты различают десять профилей и одиннадцать исполнений.

Проверяется программная CRC загруженной FLASH на netduino2, не периферийный блок
CRC STM32. E004 (выбор алгоритма) и E006 (ошибки post-build) остаются открытыми,
поведение не меняется. Старые манифесты необходимо пересобрать с ожиданиями CRC.

## Renode и общий ELF

Прошивка использует vsnprintf + SYS_WRITE0 вместо newlib SYS_WRITE/initialise_monitor_handles:
закреплённый Renode 1.16.1 не поддерживает полный набор этих semihosting-вызовов.
Это изменение тестового транспорта, не поведения фреймворка. Поле TEST_PLATFORM=cortex-m3-smoke
заменяет прежнюю жёстко заданную строку EMULATOR_MACHINE=netduino2; настоящая модель
указывается runner в команде и отчёте.

Модель [f103-smoke.repl](../../tests/firmware/renode/f103-smoke.repl) задаёт Cortex-M3,
NVIC, 64 KiB FLASH и 20 KiB RAM. RCC и FLASH controller — только memory-заглушки
для выбранного пути HAL_Init, без PLL и проверки периферии. Штатная платформа F103
Renode не используется: её широкая память и загрузка SVD по сети не нужны этому тесту.

SYS_WRITE0 обрабатывается самим Renode. [Адаптер выхода](../../tests/firmware/renode/exit_hook.py)
перехватывает экспортированный smoke_exit_trap, читает R0/R1 и блок reason/status
из RAM и останавливает CPU. Он не подставляет ожидаемый результат. Требуются операция
0x20, reason 0x20026 и статус 0/1/3 для success/failure/crc-corrupt соответственно.
Код процесса Renode обычно 0 во всех трёх случаях и сам по себе не засчитывается.

Каждый запуск имеет 0.1 секунды виртуального времени и 30 секунд предела на ПК.
Для hang нужен полный ожидаемый вывод, отсутствие гостевого exit и завершение
виртуального бюджета. Таймаут процесса на ПК всегда ошибка. Ошибки/предупреждения
Renode, незавершённый сценарий, неверные метаданные и переполнение буфера вывода
проваливают проверку. Сохраняются run.resc, process.log, firmware.log, guest-exit.json
(если был выход) и renode-summary.json. Сетевые загрузки, GUI и GDB не нужны.

```powershell
python ci/firmware_matrix.py run --emulator renode --build build/firmware-smoke --output build/firmware-renode
```

Для одного набора: `python ci/run_renode_smoke.py --build <pair-directory> --output <logs>`.
Можно задать `--renode "C:/Program Files/Renode/renode.exe"`; стандартная установка
Windows обнаруживается автоматически. В контейнере используется тот же matrix runner
с `--emulator renode` и теми же bind mounts, что для QEMU. Старые ELF/манифесты
нужно пересобрать: теперь требуется адрес символа smoke_exit_trap.

Основание ограничения: [Arm.cs в Renode 1.16.1](https://github.com/renode/renode-infrastructure/blob/add012af003a0f620d3da52828262676f374d121/src/Emulator/Cores/Arm/Arm.cs).
Дальнейшие сценарии: [план пяти групп](firmware-plan.md).

## Режимы сборки и шаблоны линкера

Четыре новых профиля используют общий тест F103C8 и протокол вывода.
`bare` и `bareTemplate` заменяют исходники на `bare_startup.S` и `main.cpp`,
явно задают Cortex-M3/Thumb/soft-float и `-nostartfiles`. Собственный ассемблерный
startup содержит векторы ядра, копирует .data, обнуляет .bss и вызывает
`__libc_init_array` перед main. В нём нет таблицы IRQ устройства и настройки
тактирования: это минимальный тест CPU, а не шаблон startup для платы.
`cmsis` и `cmsisTemplate` используют startup устройства из CMSIS и прежний
SystemInit, но отключают HAL. Новые профили не настраивают PLL и периферию.
Из изученного `cmsis-02-semihosting` взят сценарий собственного startup;
его работа с GPIO/SysTick/HSE не переносилась.

Профили с явным `.ld` резервируют heap=512 байт и stack=1K. В профилях `Template`
`linker_script: auto` находит `STM32F103C8_FLASH.ld.in` и подставляет heap=0,
stack=2K. Builder сверяет абсолютные символы линкера с эталоном, прошивка выводит
их значения. Это проверка резервирования, а не измерение пикового расхода стека
или доказательство применимости нулевой кучи к любому приложению.
CRC остаётся после всех загружаемых во FLASH данных, включая .data и .fw_version.

По `compile_commands.json` проверяется состав сборки: в bare только два собственных
исходника, без путей CMSIS/HAL; в CMSIS обязателен startup ST и исключены исходники
HAL. Отключённые библиотеки выводят `none` в метаданных. Общий перечень профилей
`ci/firmware_cases.py` не позволяет принять старые отчёты с тремя профилями за
полную новую матрицу. Неизвестные профили запуска отклоняются.

## Пользовательские библиотеки и ETL

`cmsisLibrary` добавляет каталог `Library` со своим CMakeLists.txt через `sources`
и связывает `Smoke::Library` через `link_libraries`. Статическая C/C++-библиотека
передаёт потребителю include-путь и PUBLIC-определение; PRIVATE остаётся внутри.
Флаги CPU и языков заданы явно: PRIVATE-флаги исполняемой цели не наследуются
отдельно компилируемой библиотекой. Препроцессор проверяет разделение определений
C/C++ и настройки C++ без исключений/RTTI. Проверка символов ELF требует наличия
функции C, обёртки C++ и C-пробы исполняемой цели после компоновки.

На volatile-входе `[3, 1, 4, 1, 5]` C вычисляет взвешенную сумму 46, C++ применяет
XOR 0x55: ожидается `LIB_RESULT=123`. `C_LANGUAGE=11` подтверждает вызов отдельной
C-единицы исполняемой цели. Неверные результаты дают код 4 и проваливают запуск.
`cmsisEtl` дополнительно проверяет push/pop вектора и операции строки ETL:
сумму 14, текст `etl:14`, версию из заголовка ETL. Оба профиля сохраняют проверки
startup, метаданных и CRC, используют CMSIS без HAL.

ETL 20.47.1 уже закреплена в lock-файле; builder передаёт путь include тестовому
модулю. Новые загрузки зависимостей не добавлены. Настройка HSE и бесконечный цикл
из изученного `etl-default` не перенесены. Проверяются выбранные операции
контейнеров, а не весь API ETL или поведение кучи. Специальная опция ETL во
фреймворк не вводится.

Сборка выявила [E008](errata/E008.md): языковые ключи только из профиля не доходят
до исполняемой цели. В тесте применён проверенный обход с пустыми списками в корне;
шесть configure-проб воспроизводят известное отклонение. Они не увеличивают число
сборок прошивок и запусков симуляторов на бейдже.

## Arduino String с собственным main

Автор согласовал первый этап Arduino: программные компоненты и свой main;
штатные init/setup/loop, настройка тактирования и SysTick остаются отдельной работой.
`arduinoString` выбирает настоящий backend Arduino и `use_core_main: false`.
Пользовательская обёртка `ArduinoString/CMakeLists.txt` собирает WString.cpp и itoa.c
закреплённого Core STM32 2.12.0 в Arduino::Core с настройками Arduino::Definitions.
Исходники Core не копируются и не заменяются заглушками. Компилируются только
выбранные компоненты String, а не полное ядро платы и SrcWrapper/HAL.

Toolchain независим от stm32-cmake: используется существующий тестовый toolchain
потребителя с добавлением настоящих генераторов BIN/HEX. Явно заданы Cortex-M3,
Thumb, soft-float, nano/nosys specs, `-nostartfiles`, `--gc-sections`.
`use_newlib_nano: false` отключает цель фреймворка STM32::Nano; nano выбирается
через compiler/linker specs. Прямые SYS_WRITE0/SYS_EXIT_EXTENDED не используют
файловый I/O nosys. Неиспользуемые методы String для float, требующие dtostrf,
удаляются линкером; форматирование float здесь не проверяется. Builder задаёт
core_path относительно каталога исходников, как требует backend.

Существующий собственный startup инициализирует data, BSS и конструкторы.
Ограниченная реализация `_sbrk` предоставляет 512 байт для реальных аллокаций String
без semihosting-запросов памяти. Это однопоточный тестовый аллокатор, не замена
Arduino runtime. Проверяются reserve, создание из целого, объединение, копирование,
replace, нижний регистр, поиск, substring и toInt. Ожидаются
`ARDUINO_TEXT=arm32:123` и `ARDUINO_LENGTH=9`: runner проверяет оба значения.
Ошибка внутренних проверок или неверная длина завершают прошивку с кодом 5.
Эти проверки обнаруживают и отказы выделения памяти в выбранном пути;
исчерпывающий тест нехватки кучи не выполняется. Проверки CRC FLASH и метаданных
сохранены, поля CMSIS/HAL равны `none`.

Это проверка узкого программного пути Arduino на netduino2 и той же модели памяти
Renode. Она не подтверждает работу платы F411, Arduino.h, Print, GPIO, Serial или
временных функций. Конфигурация mcu_gcs_board изучалась только для чтения как пример
обёрток и своего main; её variant F411 и драйверы устройств не переносились.
