# E007: external FreeRTOS target namespace mismatch

[Documentation](../index.md) → [Errata](index.md) → E007 · [Русский](../../ru/errata/E007.md)

**Status:** Open; the author deferred the fix on 2026-09-25. **Baseline:** `0.9.2 @ f8ef5200fc7a4a96d6f3fe9111afb8f8825474b0`. The affected discovery code is unchanged from this baseline.

Option: [`freertos_version`](../reference/0.9.2/frameworks.md#freertos-version).

## Reproduction

Using the standard stm32-cmake backend, enable FreeRTOS with `freertos_version: external`, `cmsis_rtos_api: none`, and `[ARM_CM4F, Heap::4]`. Supply a valid FREERTOS_PATH via CMake or the environment.

Tests use an F411 configuration with CMSIS enabled and the pinned `/opt/STM32Cube/Repository/STM32Cube_FW_F4_V1.28.3/Middlewares/Third_Party/FreeRTOS` directory. This is a valid source tree for discovery/namespace checks, not a separately tested external FreeRTOS distribution. An additional isolated upstream probe without STM32F4 successfully creates `FreeRTOS::ARM_CM4F` from the same tree.

## Expected and actual behavior

The intended external mode selects `FreeRTOS::*` and sources from FREERTOS_PATH. However, stm32_yml_setup_frameworks always passes `STM32${MCU_FAMILY}` to find_package. Pinned upstream `ecc5acc082effc4793eb7cbed8d8b7bd4896ca6e` therefore uses Cube discovery and creates `FreeRTOS::STM32::F4::*`. The framework then links `FreeRTOS::*`: Generate fails because `FreeRTOS::ARM_CM4F` is missing.

## Checks and limits

`configure.freertos-external-cmake-known-failure` and `configure.freertos-external-env-known-failure` require a nonzero result and Generate diagnostics naming the missing external target. Passing means reproduction of a known defect, **not working external support**. Once a fix is agreed, replace these expectations with positive checks of a real external distribution and its sources.

## Workaround and compatibility

Use `freertos_version: cube` with the corresponding Cube package for the already covered scenario; this changes the kernel source and does not automatically substitute an external package. If a separate FreeRTOS is required, discovery/custom integration needs separate verification. CMSIS-RTOS wrappers, firmware compilation and execution are not tested here. No fix or fixed release exists yet.
