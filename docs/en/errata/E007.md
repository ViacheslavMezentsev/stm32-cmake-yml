# E007: external FreeRTOS target namespace mismatch

[Documentation](../index.md) → [Errata](index.md) → E007 · [Русский](../../ru/errata/E007.md)

**Status:** Fix prepared: `3c6bfa3`, branch `claude/release-0.9.3`; not merged, no release (the fix is part of 0.9.3 per spec 4.8.6). **Baseline:** `0.9.2 @ f8ef5200fc7a4a96d6f3fe9111afb8f8825474b0`.

Option: [`freertos_version`](../reference/0.9.2/frameworks.md#freertos-version).

## Reproduction

Using the standard stm32-cmake backend, enable FreeRTOS with `freertos_version: external`, `cmsis_rtos_api: none`, and `[ARM_CM4F, Heap::4]`. Supply a valid FREERTOS_PATH via CMake or the environment.

Tests use an F411 configuration with CMSIS enabled and the pinned `/opt/STM32Cube/Repository/STM32Cube_FW_F4_V1.28.3/Middlewares/Third_Party/FreeRTOS` directory. This is a valid source tree for discovery/namespace checks, not a separately tested external FreeRTOS distribution. An additional isolated upstream probe without STM32F4 successfully creates `FreeRTOS::ARM_CM4F` from the same tree.

## Expected and actual behavior

The intended external mode selects `FreeRTOS::*` and sources from FREERTOS_PATH. However, stm32_yml_setup_frameworks always passes `STM32${MCU_FAMILY}` to find_package. Pinned upstream `ecc5acc082effc4793eb7cbed8d8b7bd4896ca6e` therefore uses Cube discovery and creates `FreeRTOS::STM32::F4::*`. The framework then links `FreeRTOS::*`: Generate fails because `FreeRTOS::ARM_CM4F` is missing.

## Checks before the fix

`configure.freertos-external-cmake-known-failure` and `configure.freertos-external-env-known-failure` required a nonzero result and Generate diagnostics naming the missing external target, i.e. they reproduced the defect.

## Fix

Fix: `3c6bfa355a7949c909cee41af22a7be8fd59960e` (spec 4.8.6–4.8.8). In `external` mode the framework calls `find_package(FreeRTOS COMPONENTS <port>)` without the family component; stm32-cmake finds FreeRTOS in `FREERTOS_PATH` and creates `FreeRTOS::<port>` and `FreeRTOS::<component>`. A missing `FREERTOS_PATH`, `FreeRTOS.h`/`tasks.c` or port files is a Configure error. Both the Cube tree and FreeRTOS-Kernel are supported; the CMSIS-RTOS wrapper comes from the family Cube package, and if it is missing Configure fails and recommends `cmsis_rtos_api: none`.

Regressions: the cases are renamed to `configure.freertos-external-cmake` and `configure.freertos-external-env` and check a successful Configure/Generate with `FreeRTOS::ARM_CM4F`, `FreeRTOS::Heap::4` and no `FreeRTOS::STM32::F4::*` (TC-22); `configure.freertos-external-kernel`, `-no-path`, `-missing-port`, `-missing-component` (TC-58); `configure.h5-cmsis-hal-freertos-external` (TC-56). Firmware build and run with FreeRTOS-Kernel are added by the `freertosExternal` profile (TC-59). Merge and release are not confirmed.

## Workaround for 0.9.2

Use `freertos_version: cube` with the corresponding Cube package; this changes the kernel source and does not substitute an external package.
